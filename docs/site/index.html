Project overview

Auditable AI Data Analysis

An AI pipeline that turns a raw dataset and a business question into a finished, checked analysis, with no code written by the user. Every number is calculated by code, every step is checked automatically, and every judgment call is explained so a person can review it and change it.

The machine does the coding. People keep the judgment.

Why the result can be trusted

Code calculates every number

The AI decides what to look at; tested code produces every figure. The AI never calculates a number: every figure it writes is traced to a tool result.

Four automatic checkpoints

Work only moves forward if it passes. Problems are flagged for a person, or the run stops and says why.

Every decision is visible

Each judgment call shows the options, the choice, the reasoning and the AI's confidence.

People stay in control

Uncertain choices are marked for review, and any decision can be overruled and the analysis re-run.

The four checkpoints: what each one protects against

◆ CHECKPOINT 1
Was the file read completely and correctly?

Counts every row, catches broken lines and wrong encoding. Stops a bad file before any AI cost.

What it checks
  • Lines in the file = rows loaded + rows rejected
  • Rejected lines: flag above 0.1%, block above 1%
  • Unique column names; file hashes recorded
  • Every column has a type, or a reason why not
  • Statements in the brief hold in the data
◆ CHECKPOINT 2
Is the cleaned data safe to analyse?

No rows lost or values blanked without explanation; re-running the fixes gives the same result.

What it checks
  • Types and columns match the diagnosis
  • Every changed cell and removed row is accounted for, with a reason
  • Untouched columns are identical to the raw data
  • Row loss: flag above 5%, block above 20%
  • The target is never filled in; replaying the log reproduces the result
◆ CHECKPOINT 3
Can the analysis plan actually run?

The columns exist, the methods can run on this data, and excluded data is not used.

What it checks
  • Every column exists; every method is a tested tool
  • The target is the brief's; IDs, personal data and excluded columns are not analysed
  • A column that gives the answer away is excluded
  • Enough rows for each question, or it is marked not possible
◆ CHECKPOINT 4
Is every claim backed by a calculation?

Each number in the text is traced to a tool result; no overclaiming. Only checked text reaches the report.

What it checks
  • Every question in the plan is answered
  • Every finding cites tool results that ran
  • Every number matches a logged result; a number the AI worked out itself is rejected
  • A finding without real evidence cannot be called strong
PASS all good, continue
FLAG continue, shown for review
BLOCK stop, and explain why

Why this design matters

AI is good at judgment but can make up numbers. Here the two are separated: the AI never calculates a figure, and code never makes a judgment call. Each hand-over between stages follows a fixed format, so the checkpoints can verify it mechanically.

Where the person comes in

Every judgment call is written to an editable decision list (decisions.yaml), and the analysis plan can be edited too. Change a choice, or write it into the brief, and run again. The machine redoes the work; your call is the one that counts.

05

Monitoring every AI call

Each run folder is the audit trail of one analysis. On top of that, every AI call can be traced in Langfuse: which specialist made it, with which model, what it was sent and answered, the tokens, the cost and the time. That shows where money and time go, and what changed after a model or prompt was swapped. Tracing is optional and can never stop a run.

What it shows, and what it is for

  • Cost control: the analyst is two thirds of the cost, because each round of tool calls re-sends the earlier results. That is the first place to save.
  • Model choice: each specialist has its own model. On the cheaper model, the coder, reviewer and planner cost about half of what they did in an earlier all-Opus run (on a different dataset, so a first indication, not a measurement).
  • Debugging: the exact prompt and reply behind a weak finding or a blocked checkpoint.
  • Next: attach checkpoint outcomes as scores, so quality and cost sit side by side.

Only what the AI is sent is traced: column names, summaries and the brief, never the rows.

The context steers the method

The fraud dataset's notes say the balances of fraudulent transactions were annulled. With no explicit exclusion in the brief, the pipeline read this from the dataset's description and excluded the four balance columns, which would otherwise have given the answer away. It also set aside the existing fraud flag, which fires on only 1 in 200,000 rows.

Known limits

Associations, not causes. Validated so far on three well-known datasets the AI may have seen before. It analyses the columns it is given and does not create new ones (such as hour of day). A working prototype: local, single user, files only.
